# MacinRender 播放集成

Player 将 AC-4 Core 的 Scene 转换为 renderer-native Scene，经 MacinRender C ABI v1.39
进行空间渲染及设备输出。Core 类型和平台指针均不进入 GUI；FFI 封装集中在独立 crate。

## 播放策略

- 自动模式：Windows 使用原始动态对象直通，macOS 使用系统空间音频。
- 系统空间音频：SAF VBAP、Apple 几何；开放 7.1.4、9.1.6、22.2，默认 7.1.4。
  22.2 默认将单路 LFE 以每路 `1/sqrt(2)` 复制到双 LFE，也可选择 direct。
- 软件双耳：SAF HRTF，默认内置 KEMAR，可选择用户 SOFA。
- 系统模式跟随系统默认输出。Windows 的固定床超出静态槽位的位置采用所选 Apple 几何；
  静态槽位的最终角度由 Windows 的空间化器决定。
- 软件朝向在 Mac 优先使用 AirPods，缺失或权限不可用时使用手动朝向；Windows 使用手动朝向。
  系统空间音频模式保持上游中性姿态，macOS 的系统头追由系统负责。

软件双耳的设备输出在主音量之后使用两耳联动的采样峰值保护：5 ms 前视、100 ms 释放，
上限为 -1 dBFS。自定义 SOFA 的增益和多对象叠加可能让浮点双耳输出超过满幅；保护器会在
miniaudio 硬限幅之前平滑降低两耳增益。未触发保护时按原音量逐采样通过，低音量不会被
预先限幅。前视缓存保留暂停位置，并在 seek/新 epoch 时清空；结尾完整排出，媒体帧数不变。
原生 Scene 的浮点拉取仍保留超满幅数据，系统空间音频交由系统处理最终输出。

## 设置面板分页

Audio settings 的内容按**播放模式**分页，页签由 `OutputPage::of` 给出：系统空间音频是
`Speakers` / `Head`，软件双耳是 `HRTF` / `Headphones` / `Head`，其余（Windows 对象直通、
以及无原生输出时的 Automatic）只有 `Head`。播放模式自己不是页签——它决定有哪些页签，
所以留在页签栏上面的固定行里。只有一页时不画页签栏。

分页解决的不是「短一点」，而是**导航是否会被内容推走**。这些块原来是按模式逐个 `if` 堆在
一列里，窗口高度是它们的和；换成折叠标题也只是把导航放进内容流，一个自己就比屏幕高的块
（`Headphones` 展开约 750 pt）照样能把它下面的标题顶出屏幕。页签栏在内容之外，位置与任何
一页的长度无关。

记住的页签不随模式变化即时纠正，而是画的时候由 `OutputPage::resolve` 解析：当前模式有这一页
就用它，没有就用该模式的第一页。因此绕到别的模式再回来，原来那一页还在。初值取 `Speakers`
——它不属于双耳的任何一页，于是双耳会话开在自己的第一页而不是两种模式碰巧共有的那一页。

`Headphones` 一页本身按「选 → 调 → 看结果」再分三段（`draw_hptf_chooser` /
`draw_hptf_knobs` / `draw_hptf_response`），这也是三者相互依赖的顺序：ghost 画哪一份由选择页
报出的悬停行决定，曲线画什么由旋钮决定。写盘那一步是 `stage_tuned_profile`，不碰任何应用状态，
因此那条 `#` 来源注释与文件名可以脱离 GUI 直接测。

## 耳机补偿（HpTF）

载入 AutoEq 的 `ParametricEQ.txt`，由渲染器把它设计成双二阶级联，施加在交给耳机的两声道上。
**只有软件双耳可用**：多声道扬声器输出和系统空间音频把床交给操作系统做 HRTF，最终两声道不在本侧
生成，原生接口对这些输出返回 `ADM_ERROR_UNSUPPORTED`——是一个可显示的状态，不是失败。Windows
对象直通不经过 MacinRender，同样没有这一级。

补偿位于输出限幅器**上游**，被抬高的频段仍由 −1 dBFS 天花板保护。它刻意不进入 LUFS 表——换耳机
不应改变节目响度读数——但会改变 peak/RMS，因为那反映设备真正收到的信号。播放器自己的逐对象表头
读的是 Scene 帧，在渲染之前，本来就不受影响。

只支持 `ParametricEQ.txt`。AutoEq 的最小相位 `.wav` 需要约 2048 taps 才能把截断误差压到 0.1 dB，
要分块 FFT 卷积；十段双二阶约 60 flops/frame 且无依赖。两种格式**不是同一条曲线**（宽带约 1 dB、
20 kHz 约 3.2 dB），同时提供而不做电平匹配只会产生"哪种格式更好听"的伪结论。

### 响应曲线

设置里画出当前 profile 的级联响应，**把 preamp 和实际生效的额外衰减折进去**：顶线是满刻度，曲线到顶线的距离就是 preamp
买来的余量，图上的峰值就是渲染器报的 `max_response_db`，而不是一个形似的别的量。坐标轴固定
+3…−12 dB，只在曲线超出时才扩展——隔一会儿再载入另一份 profile，两条曲线仍要能用眼睛直接比，
自动缩放会悄悄毁掉这一点。

曲线由 `hptf_profile.rs` **独立解析** ParametricEQ 得到：同一份文档化格式的第二套实现，词表、默认 Q、
容错规则（跳过空行与 `#`、`OFF` 段不进级联、未知类型跳过、坏数值报错）都照渲染器的来。两套读法互相
对账，一共两道，都以渲染器为准——这正是 `backend::state` 用 `ebur128` 对账 K 加权的同一种做法。

**第一道在解析时**（v1.38 `adm_hptf_parse_parametric_eq`）。它不需要输出、不开文件，所以读到文件的那
一刻就能比，连 ghost 也能比。两边拿到的是**同一段文本**而不是同一个路径，"文件在中间改过"因此不成其
为解释。逐段比：类型、Fc、Gain、Q，外加 preamp 和启用段数，报第一处差异并指名到段——"两边不一致"没法
让人动手，"第 7 段的 Q"可以。四种结果都有话说：都读通而有出入、渲染器读不了这份、本侧读不了而渲染器
读得通（那说明错的是本侧），只有"两边读出同一件事"才什么都不说。

**第二道在运行时**：段数、preamp 和峰值这三项渲染器都会回报，运行中的曲线逐点叠加 `auto_trim_db`
后再对比峰值，开启自动衰减也继续校验。尚未运行时仅绘制文件响应，若勾选自动衰减，图上明确标明这是
衰减前的预览。解析对账命中时不再显示运行对账——前者指名到段，而后者这时只会把同一处毛病说成峰值挪
了位。

对账已经抓到过两处本侧的偏差，都已改掉：启用段数超过 32 时渲染器**拒收**而不是截断，`Preamp:` 必须
是有限数。

biquad 的响应与采样率有关，所以曲线按「路径 + 设计采样率」缓存，两者任一改变都重新读文件；没有
运行中的输出时按 Scene 输出固定的 48 kHz 绘制。当前这条和 ghost 各占一个槽位，扫过整个列表
也只在换到另一行时才读一次文件。「Refresh profile folder」连同槽位一起清掉，免得改过的文件还留着旧图。

悬停 `hptf/` 列表里的另一份，把它的曲线淡淡地画在当前这条后面，坐标轴同时覆盖两条——画到框外的对比
比没有还糟。它**只是画出来**：`set_hptf` 收不到任何东西，所以翻文件夹不会把正在试听的那一份交叉淡化
掉。峰值点只标当前这条，因为那个点是要拿去和渲染器对账的数，而 ghost 并没有在跑。指针停在已经选中
的那一行上不画 ghost——点一行之后指针仍停在它上面，选中的那一帧同时也是悬停的那一帧。没有选中任何
profile 时，ghost 就是整张图。

ghost 按文件原样画，不叠 `auto_trim_db`：那份衰减是渲染器为**正在跑的**那一条算出来的，套到另一份
上就是编造。当前这条确实带着衰减时两条线不是同一种量，图例给 ghost 标上 `as written` 说明这一点——
和未运行时标"衰减前"是同一条规矩。

### 两个旋钮

profile 之上给使用者两个控制，**只给两个**。这是个检视工具，摆十段 biquad 让人捏，会和它其余每一个
决定作对；两个有名有姓、可核对的旋钮不会。

**Bass**：105 Hz、Q 0.70 的低架，±6 dB。这两个数字就是 AutoEq `--bass-boost` 用的那一个架——所以
把一份 `wo_bass` 的 profile 加 +6，得到的是它发布的那份预设本身，而不是"差不多"。旋钮因此是可核对的。

**Tilt**：绕 1 kHz 的直线斜率，±2 dB/oct。

斜率这个控制值得说清楚，因为**显而易见的做法是错的**。一对共用转折点的高低架（"tilt EQ"的常见实现）
根本不是恒定斜率：Q 0.707 下它在 300 Hz 以下和 3 kHz 以上各自压平，实测对 −1 dB/oct 的直线最大差
**5.9 dB**，对 ±2 dB/oct 差 11.5 dB。在图上印一个 dB/oct 的数字，那不是含糊，是假的。

恒定的 dB/oct 是分数阶响应，不是双二阶。做法是把若干低架的转折点摆到**被倾斜的频段之外**，让 20 Hz–
20 kHz 落在阶梯连成的那段直线上。本侧用三段，Q 0.38，转折点按 1 Hz–20 kHz 等比分布（5.2 / 141 /
3839 Hz），每段增益 `-tilt · log2(20000/1) / 3`。实测：44.1 / 48 / 96 kHz 三个设计率下，±1 dB/oct 偏
直线不超过 **0.25 dB**，±2 dB/oct 不超过 0.50 dB。`the_tilt_is_a_straight_line_in_log_frequency`
钉的就是这件事，也正是面板敢印 dB/oct 的全部依据。

低架叠出来的阶梯整体抬升响应而不是绕轴翘板，所以还要把这份抬升从 preamp 里扣回去，否则"倾斜"就变成
了倾斜加音量。扣多少是**测出来的**：每 dB/oct 抬 4.38 dB，从 44.1 kHz 到 192 kHz 只动 0.02 dB，所以
一个常数够用。理想阶跃会是 `log2(20000/1000) = 4.32`——真实的架不是阶跃，差的就是这 0.06。低架不需要
这项补偿：把低频抬起来正是它的全部用意。

### 派生段附加，不并入

旋钮产生的段**附加在 profile 的级联后面**，一路到渲染器都不并进去。两边都不出手时走原路：
`adm_scene_output_set_hptf_ex` 读文件，也就是 v1.39 那条不占输出控制锁的路——把旋钮转回零，恢复的
是和没有旋钮的版本完全相同的路径。任一旋钮离开零点，则由 `hptf-preparation` 线程读文件、本侧解析、
附加派生段，走 v1.38 的 `adm_scene_output_set_hptf_parameters` 下发内存中的级联，不再经文件。

profile 的段数加派生段超过 32 时**拒绝**而不是丢弃尾巴，理由和解析时一样：渲染器会拒收，画一条它不会
播的曲线比报错更糟。

面板上派生段单独计数（`10 bands + 4 adjustment`），旋钮不在零点时用虚线另画一条"profile 本身"。文件
要的和使用者要的，任何时候都分得开——这正是这块面板拿掉"compensation"一词的那条道理。

### 存成 profile

「Save as profile…」把 profile 加调整写成一份普通的 ParametricEQ 文件，经**现有的导入路径**进 `hptf/`，
选中它，旋钮归零。调好的设置于是变成一份正常的、有哈希有索引、可以拷给别人的 profile，而不是
`settings.json` 里两个别人看不见的数。

数字按「读回来仍是同一个 double」的长度打印——通常两位小数，偶尔十七位。派生段的转折点（5.196…Hz）
不是谁打出来的数，为了好看四舍五入就是存了另一份东西。`a_saved_profile_reads_back_as_the_very_same_cascade`
比的是 `to_bits()` 而不是容差：存下来的必须**就是**刚才在听的那一份。

来源写在 `#` 注释里（两边解析器都跳过），文件名同时带上来源和做了什么——
`Sony_MDR-MV1 (bass +2.5 dB, tilt -1.00 dB per octave).txt`。合并之后，这两处是仅剩的记录。内容完全
相同的两次保存由导入路径按哈希去重，不会多出一份。

选中新文件和旋钮归零是**同一次** settings 变更。分开做会有一帧用着已经烘进调整的新 profile、旋钮却
还在原位，等于把调整叠了两次。暂存目录一直活到导入读完为止，它的存在本身也是「这次导入是一次保存」
的标记。

### 目标由文件决定，播放器不作断言

profile 里只有一行 `Preamp:` 和若干 biquad，**不携带目标曲线或测量来源**。同一副耳机、同一支人工头，
换一条目标就是完全不同的一份文件，而播放器无从分辨。因此设置里只显示文件名，以及实际生效的段数、
preamp 和 `max_response_db`——都是能从运行中的级联读回来的事实——不出现"补偿到某某目标"这类它验证不了的说法。

选哪条目标是使用者的事，但要和 SOFA 的参考场配套才有意义。补偿是 `target − raw`：只要目标和测量出自
同一支人工头，耦合器自身的响应在相减时抵消，所以不同装置算出的补偿彼此可比；**但不能把一支装置的目标
套到另一支装置的测量上**，那会把两者的响应差整个灌进曲线。

SADIE D1 KU100 这类做过扩散场均衡的 HRTF，应配扩散场目标的 profile：方向无关成分两边对消，留下的才是
携带定位的方向相关部分。AutoEq 仓库发布的预设目标是 Harman over-ear 2018，并且显式加了 6 dB 低音搁架
（其命令行是 `--target=..._wo_bass --bass-boost=6`），用在这条链路上等于额外叠一道低音抬升和高频下倾——
听感上更讨好，但不是 HRTF 假定的参考。内置 KEMAR 的均衡状态上游未作说明，默认路径上的配对关系因此没有保证。

解析与系数设计在调用线程同步完成，坏文件直接报错，不打扰音频线程；播放器为此使用独立的
`hptf-preparation` 线程，通过 v1.39 的 `adm_scene_output_set_hptf_ex` 准备补偿。

v1.38 的内存参数接口也已绑定：`adm_hptf_band_t` / `adm_hptf_parameters_t` 两个 POD（连同 size 与
offset 一起进了 `abi_probe.c` 的布局对拍），`parse_parametric_eq` 走一次性 context 把 AutoEq 文本解析到
调用方的数组里（先问段数再取值的两次调用），`Control::set_hptf_parameters` 直接下发内存中的级联、不经
文件。目前只有解析这半边有调用方——就是上面那道解析对账；下发那半边留给需要它的编辑界面。
此接口独占每次调用的错误字符串，准备时不持有 Rust 共享 gate 或原生输出控制锁，慢读取与系数设计
不阻塞 Scene 提交、状态、暂停或音量；仅最终发布使用原生短锁。播放器串行化准备请求并携带 revision，
仅成功请求更新等待回调确认的 revision，失败不会覆盖最后成功的配置。换档位在 2048 帧窗口内线性混合两条级联，
即时生效不等 ring 排空；一次只有一个切换在途，最坏应用延迟为两个窗口。seek 的滤波器状态由原生
`begin_epoch` 连同峰值保护一起重置，播放器无需参与。

`Preamp:` 策略有两档。默认严格使用文件里的数值；`auto_trim` 按 20 Hz–20 kHz 幅度响应的保守上界
再压一点——这是频响界，不是瞬态限幅。设置里显示的 `max_response_db` 高于 0 表示该曲线可能触到天花板。

生效状态从输出实时派生，与 SOFA 同一套语义：选中不等于生效，`applied_revision` 回显到播放器
送出的 revision 才算 **in use**。渲染器能让补偿跨自己的后端和设备切换存活，但播放器重建输出
（换模式、换设备）会得到一个全新的输出对象，其上没有补偿，因此每次装载设置和每次建好输出都
重新对账一次。准备期间保存请求和最后成功配置各自的身份；失败时恢复最后成功配置及 preamp 策略，
保留实际生效状态，并允许修正文件后再次选择同一路径。

## 内容指定的逐对象头追

Player 消费 Core 的有效 `headphone_policy()`，只使用其中的跟踪参照系。`SceneRelative`
参与 world-to-head 逆旋转，`HeadRelative` 通过 renderer 的 `head_locked` 跳过补偿。
`Unspecified` 正常使用场景固定默认值；`Unsupported` 保留原因并按场景固定降级，诊断按当前
呈现时间显示。两者不启动新的头姿来源，也不自动切换输出。Bypass/Near/Mid/Far 继续不参与
播放器的声学处理；这些模式本身不会导致静音。

Player 调用 `semantic_complete(SemanticScope::Spatial)` 保留非耳机语义检查；缺少初始状态的
预热仍然不可播放。Core 的 `All` 检查和完整语义诊断保持严格含义，不被播放器降级改写。

`decoder::metadata` 在进入 FIFO 之前续接跨帧的位置与增益渐变；每个 block 携带当前起点和
各字段剩余目标。原生引擎保留有效 changed-fields，双耳各字段与 VBAP 的电平/声像分别计时。
头追字段在事件偏移处离散切换，不重启连续渐变。裁剪从这份统一时间线恢复剩余目标。

元素编号以黑色表示场景固定、白色表示头部固定，方块及轨迹沿用既有配色。未指定或降级为场景固定的对象使用黑色编号。
场景上方的两项统计来自与图形相同的呈现时间快照，统计全部对象（含超出显示上限的对象，不含 LFE）；
场景固定数量包含未指定及降级对象，尚无当前播放快照时显示破折号，暂停时保留当前数量。
场景镜像保留对象参照系及其轨迹，绘制时将跟头对象正向旋转到世界坐标；参照系改变清空该对象
轨迹，只有瞬时位置事件绘制跳变。Windows 对象直通按输出 quantum 应用相同跟踪策略。
系统空间音频的固定床不能保留逐对象跟头语义；出现相关内容时提供能力提示及软件双耳切换按钮，
用户选择的输出保持不变。没有专门的“3DOF 文件”识别或额外开关。

## macOS 控制中心 Atmos 标识辅助

`atmos_label_assist` 默认开启并随音频设置持久化。**控制中心的「杜比全景声」标签仅在
macOS 系统空间音频的 7.1.4 输出时生效**，9.1.6 和 22.2 不生效。

辅助链仅在 7.1.4 系统空间音频输出时可启用。9.1.6、22.2 和软件双耳不启动辅助链，
设置中的开关不可用；切回 7.1.4 系统空间音频输出会恢复用户保存的选择。
开关热切换不重建 AC-4 解码器或主音频输出。

播放器在确认主音频呈现位置推进后，在同一进程启动公开 AVFoundation API 构建的静音
AVQueuePlayer。每个播放项独立安装 post-effects MTAudioProcessingTap，正常及错误路径
均清零输出；辅助链不消费 Scene FIFO，也不向 ASBR 传递音频。两个播放项循环使用内置
自制 JOC 文件，来源与摘要见 `assets/audio/`。每个播放项的连续时间线为 24 小时 46.08 秒：
MP4 sample table 将同一组 30.016 秒压缩包引用 2880 次，`mdat` 仅保留一份，文件约 1.45 MB。
原来的短文件每约 30 秒更换播放项和 tap；AirPods 实听报告开启辅助时偶发断音、关闭后正常。
长时间线移除了这些频繁交接，包引用交界不更换 AVPlayerItem、解码器或 tap。24 小时后的
播放项交接仍保留原有队列补充逻辑。2026-09-09，用户在当前 AirPods 的 7.1.4 系统空间音频
回放中重新开启标签辅助，确认不再出现此前的断音。编码器不是构建或运行依赖。

辅助状态由 SpatialOutputController 管理；准备备用输出不会启动辅助播放。暂停会释放辅助
播放项，因为单独 AVQueuePlayer.pause() 的实测仍会触发 tap 取样；恢复时重新建立辅助链。
seek、换曲、输出重建、结束及禁用会取消旧 generation，延迟完成的加载不能重新启动旧链。
默认输出设备改变后等待主 PCM 再次推进，再重建辅助链。辅助错误只显示在诊断中，不改变
主回放的成功/失败状态；本轮不自动重试，下一会话、设备变化或用户重新启用时再尝试。

原生代码静态链接在播放器自身的桥接 crate 中，不改变上游 MacinRender 公共 C ABI。
原生控制在主队列执行；Rust 析构只排入异步清理，不等待主队列。诊断的 Active 指辅助链
运行状态，并非对控制中心显示文字的自动检测。

`python3 scripts/test_atmos_asset.py` 验证素材可重现、压缩包逐字节不变，并在安装 FFmpeg 时
独立校验重复引用交界和 24 小时尾部的时间戳及包哈希。
`bash scripts/test-atmos-assist.sh 610` 验证真实原生加载、故障注入、异步取消、暂停恢复、
跨过 20 次原短素材交界而不更换播放项，以及 30 次重启后的资源回收。另用仅限测试的
一秒播放项验证最终队列交接。实际系统标识、听感和设备切换需在正式 `.app` 和对应耳机上另外验证。

## 时间线与线程

Scene FIFO 始终只有一个消费者。软件渲染路径由独立 producer 线程提交 PCM，保留有界的纯元数据
历史；图像位置按设备呈现进度解析。ASBR 的 PTS 时钟与渲染器已经 pull 的帧数独立，队列里的
未播放音频不推进 GUI。实时 callback 路径使用上一周期消费进度，精度明确为 callback 级。

Core 的元数据 bitmask 逐字段转换（例如 Core POSITION=bit 3，而 renderer POSITION=bit 2）。
重叠裁剪保留进行中的 ramp；缺口提交显式静音 Scene；seek 的 epoch 屏障同时清理设备及渲染队列。
软件路径允许 generation 在帧边界改变拓扑；同 generation 内改变元素集合会报错。

重播与跳回播放时间零点时，通过保留的文件句柄读取首个编码 AU 开始解码，保留 MP4 priming 所需的预卷。
不能直接跳到呈现时间为零的较晚同步样本，否则可能缺失 A-SPX 的跨帧历史。解码失败后，播放按钮
允许显式从头重试；重试复用打开的文件与索引、创建新的 Core 会话，并用新 epoch 丢弃旧事件与 Scene。
中途定位时，先在解码线程内验证与正常起播相同的预缓冲量，再发布 PCM、元数据与就绪事件；若随机访问点
缺少延迟控制所需的历史，可在发布之前退回更早的起点重试。剩余媒体不足预缓冲量时，在确认 EOS 后发布尾部。
解码失败会取消未完成的输出准备与交接、保留切换前的设置并重新启用设置控件，不会一直等待已销毁输出的就绪通知。

SOFA 热切换在独立加载线程进行，使用拥有独立错误结果的 C ABI，避免阻塞送音或播放进度。
需要更换输出格式时，先在后台准备暂停状态的新输出，旧输出继续播放；准备成功后才从当时的呈现位置
进行安全 seek 和交接。准备失败或原播放 epoch 已改变时丢弃候选输出。SOFA 文件选择使用异步对话框。
实时双耳渲染器复用有界的只读 HRTF 缓存（最多四组、64 MiB），SOFA 路径、文件时间和大小变化会使缓存失效；
FFT 工作区、卷积尾部及对象状态仍由每个渲染器独立持有。
实时双耳的对象运动与头追共用连续 HRTF 查表及输入历史卷积：相邻角度间连续插值，
新旧滤波器处理同一份完整输入历史，并保留插值后滤波器的全部响应。头姿等突变目标使用
持续 10 ms 的交叉渐变，连续对象元数据仍按各自的采样时间渐变。增益和 diffuse 在输入端
逐采样处理；静音尾部和跨帧历史不会在转头或对象运动时重新拼接。HRTF 幅度在初始化时缓存，
同样计入只读缓存的 64 MiB 上限。
实时路径在 FFT 与插值表准备完成后释放原始时域 HRIR 和测量方向数组，缓存只保留回放需要的
频域 HRTF、预计算幅度与压缩插值表；离线 SAF spreader 仍保留其需要的时域数据。以 48 kHz、777 方向、
双耳各 1024 taps 的数据集计算，每份实时缓存可释放约 6.1 MiB 原始数据，释放操作不改变已准备好的滤波器或采样精度。
头追改变预渲染上限时，生产端与消费端使用同一个有效起播门槛；已有缓冲达到新上限也会立即发布就绪，
避免循环重启时停在零帧并等待头追更新超时。输出尚在缓冲时，状态栏会明确显示缓冲状态。
原生采集在自己的 NSOperationQueue 接收传感器回调，Rust 只轮询快照；停止时先排空回调。

独立头部控制线程使用 canonical X-right/Y-front/Z-up 四元数，yaw 绕 Z、pitch 绕 X、roll 绕 Y，
构成为 `Rz(yaw) Rx(pitch) Ry(roll)`。音频使用 world-to-head 逆旋转；场景保留世界坐标，角色
头部使用正向旋转。相机的 orbit/pan 不修改听者。窗口隐藏时传感器处理继续运行。

## 原生源码构建

默认 feature 包含 `decode` 和 `macinrender`。Cargo 调用 CMake/Ninja 构建固定提交的源代码；
原生库使用 Release，开启 SOFA，关闭 CLI、测试和 IAMF。macOS 使用 Accelerate；Windows
需要 MSVC、Boost 头文件及 OpenBLAS/LAPACKE，沿用 MacinRender 的 Windows 工具链。

可设置以下开发覆盖，避免修改锁定版本：

```text
MACINRENDER_SOURCE_DIR=<本地 MacinRender 源码目录>
MACINRENDER_FETCHCONTENT_DIR=<Cargo target 内的依赖缓存目录>
```

Windows 的 `CMAKE_TOOLCHAIN_FILE`、`OPENBLAS_LIBRARY`、`LAPACKE_LIBRARY`、
`OPENBLAS_HEADER_PATH`、`LAPACKE_HEADER_PATH` 会传入 CMake。配置缓存与产物位于 Cargo 构建目录。
没有 `macinrender` 时不需要 C++ 依赖：`cargo run --no-default-features --features decode` 保留
Windows 对象直通以及 macOS/Linux 场景预览。`--no-default-features` 为纯检查构建。

```bash
cargo build --release
python3 scripts/package-player.py
```

播放器直接静态链接 MacinRender C API 与头追桥接源码；完整传递依赖由 CMake File API 提供。
Mac `.app` 包含运动权限声明及本地签名，Windows 载荷只有 EXE，许可内嵌于 About。
安装包检查实际载荷、系统依赖、原生渲染及图形窗口，详见 [安装包与 CI](PACKAGING.md)。
macOS 包使用圆角像素图标，Windows 可执行文件嵌入直角方块图标；窗口图标直接编译进程序。
图标源文件和再生成方式见 [应用图标](../assets/icons/README.md)。Windows 构建还需要 SDK 的资源编译器，
MSVC 构建会自动查找 `rc.exe`。
裸 `cargo run` 缺少应用权限声明时，AirPods 采集明确显示不可用并使用手动朝向。软件双耳模式
首次检测到支持设备时可能出现系统运动权限提示。实际三轴方向还应通过 AirPods 真机听验确认。
